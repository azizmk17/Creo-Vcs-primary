# Nexus Exact Revision, Iteration, and Assembly Binding Workflow

## Purpose

This document describes the object-versioning model used by Nexus for Creo parts,
assemblies, drawings, and BOM structures. The purpose is to make every checked-in
assembly reproducible: Nexus must be able to answer exactly which child versions were
used by a particular assembly iteration, even after newer child versions are created.

The BOM item remains the PLM object. Files, project versions, commits, snapshots, and
baselines support the object but do not replace its revision and iteration identity.

## Core Terms

### BOM item

A persistent engineering object such as a part or assembly. It owns attributes such as
AES number, part number, type, material, categories, associated files, revision history,
and lifecycle state.

### Revision

A controlled design generation. Nexus accepts company revision schemes such as:

- `A`, `B`, `C`
- `A0`, `A1`
- `A010`, `A020`
- Other codes containing letters, numbers, dots, underscores, or hyphens

A released revision is immutable. Further work either uses **Create New Revision** or
checks out the Released item with an approved target revision. In the second workflow,
the Released iteration remains current until commit creates the target revision.

### Iteration

A checked-in checkpoint inside a revision. Iterations are generated by Nexus and are
never typed or renamed by the user.

Examples:

```text
A.1 -> A.2 -> A.3
A010.1 -> A010.2
```

Creating revision `B` explicitly creates `B.1`. A checkout started directly from a
Released item creates `B.1` only when its commit is finalized. Every later successful
commit creates the next iteration in that revision.

### Exact child binding

Each checked-in assembly iteration stores the exact revision and iteration of every
direct child usage.

```text
MOTOR ASSEMBLY C.4
|- SHAFT B.3
|- COVER A.2
`- SCREW A.1, quantity 4
```

If `COVER A.3` is later created, `MOTOR ASSEMBLY C.4` remains bound to `COVER A.2`.
No historical assembly changes automatically.

### Working configuration

When an assembly is checked out, Nexus creates an editable working configuration from
its current checked-in bindings. Structure edits and child-version updates modify this
working configuration. It becomes permanent only after a successful commit.

### Project version

Project versions such as `A - WIP`, `B - WIP`, and `C - Released` are complete project
configurations. They are not item revisions. Creating a project version copies and
remaps the item revision history, iterations, usages, and exact child bindings to the
new project rows.

### Creo filename iteration

Creo filenames such as `cover.prt.17`, `motor.asm.8`, and `cover.drw.4` are Creo file
iterations. They are not Nexus PLM iterations.

```text
Nexus object version: COVER A.3
Referenced Creo file: cover.prt.17
```

Nexus records the file pointer in the object checkpoint, but it never assumes that
`.17` means PLM iteration `.17`.

### Attachment version

PDF, STEP, drawing, and other managed attachments have their own `version_no` history.
An attachment version is not an object iteration. Releasing one attachment does not
release the BOM object.

## Lifecycle Rules

1. An In Work revision can be checked out directly.
2. A Released item can be checked out only with a unique target revision. The Released
   iteration stays immutable; working changes become `<target>.1` on commit.
3. Structure changes require the affected assembly to be checked out.
4. Moving a child between assemblies requires both source and target assemblies to be
   checked out.
5. Check-in occurs only through successful commit finalization.
6. **Undo Checkout** is not check-in and creates no iteration.
7. A newer child iteration never changes an existing assembly binding automatically.
8. A user must explicitly adopt a newer child through **Update Child Versions**.
9. Releasing a revision freezes its current object attributes, file pointers, and exact
   direct-child configuration.
10. A new revision starts at iteration `.1` and copies the released configuration.
11. Undoing a Released checkout deletes the pending revision intent and restores the
    Released object without creating revision history.

## User Workflows

### Modify a part

1. Select the part in the BOM.
2. Click **Check Out**.
3. Modify the Creo native file and any permitted BOM attributes.
4. Create a commit through the Commit page.
5. Complete the existing validation and merge workflow.
6. Commit finalization releases the lock and creates the next PLM iteration.

Example: `SHAFT B.3` becomes `SHAFT B.4`.

Submitting or validating a pending commit alone does not create a checked-in object
iteration unless the normal commit finalization/merge completes.

### Modify a Released item

1. Select the Released part or assembly and click **Check Out**.
2. Review the warning and enter the approved target revision. Nexus proposes common
   sequences such as `A -> B`, `Z -> AA`, `A0 -> A1`, and `A010 -> A020`; the value is
   editable for company-specific schemes.
3. Nexus locks the item but keeps the Released revision and iteration current.
4. Make the Creo and BOM changes.
5. Commit normally. Commit finalization creates `<target revision>.1`, captures the
   changed Creo filenames, and releases the checkout.

If Undo Checkout is used, Nexus restores the Released iteration and removes the target
revision intent. No new revision or iteration is created.

### Modify an assembly structure

1. Check out the assembly.
2. Add, remove, move, copy, or reorder direct children.
3. When moving between assemblies, check out both assemblies first.
4. Review the Structure tab and its Bound, Latest, and Binding columns.
5. Commit the changed assembly.
6. Nexus creates the next assembly iteration and snapshots quantity, order, and exact
   child versions.

### Adopt newer children

1. Check out the parent assembly.
2. Open the Structure tab.
3. Click **Update Child Versions**.
4. Review each direct child's **Bound** and **Latest** versions.
5. Select only the versions intentionally being adopted.
6. Commit the assembly.

Before commit, the update is part of the working configuration. The previous assembly
iteration is unchanged.

### Undo checkout

Use **Undo Checkout** when the working changes must be discarded.

Nexus will:

- Restore the last checked-in BOM attributes.
- Restore the last checked-in direct-child structure, quantity, and order.
- Discard working child bindings.
- Release the lock.
- Record an `undo_checkout` audit event.
- Keep the current revision and iteration unchanged.

Undo Checkout does not create a check-in event or a new iteration.

Nexus does not delete unreferenced Creo trail files from the working directory during
Undo Checkout. Automatic deletion would be unsafe for family tables and shared working
directories. The checked-in BOM file pointers are restored; local Creo cleanup remains
a controlled workspace operation.

### Release a revision

1. Ensure the object is checked in and has no active checkout.
2. Resolve release-blocking critical issues.
3. Click **Release Revision**.
4. Enter a release note and confirm.

The exact current iteration is frozen. The assembly may intentionally reference an
older child iteration; Nexus does not silently update children during release.

### Create a new revision

1. Start from a released revision.
2. Click **Create New Revision**.
3. Enter the next approved company revision code and a reason.
4. Nexus creates `<new revision>.1` from the released object and child configuration.
5. Check out the new revision before changing it.

The old released revision and all its iterations remain unchanged.

## BOM Structure Display

The main BOM uses **Rev/Iter** to display the current object version, for example
`A010.2`.

An assembly with newer direct-child versions displays a `v+N` marker beside its name,
where `N` is the number of direct bindings that can be updated. The tooltip explains
the count. A working binding already updated to Latest is no longer counted.

The Structure tab displays:

- **Current**: the child's current object version.
- **Bound**: the child version used by this parent configuration.
- **Latest**: the latest available child version.
- **Binding**: `Current` or `Update available`.
- **Source** in the update dialog: `Checked In` or `Working`.

Where Used continues to show direct parent usages. It does not claim that every
ancestor directly uses the selected component.

Right-clicking a BOM item provides **View Latest CAD Files**, which shows the native
Creo and drawing filenames captured by the current object iteration. Right-clicking a
Structure row provides separate **Current**, **Bound**, and **Latest** CAD-file views.
These commands resolve immutable iteration snapshots; they do not substitute filenames
from the current working BOM row.

## Creo Family Tables and Shared Native Files

Nexus already groups BOM rows that share the same base Creo native filename. Checkout,
commit finalization, release, and new-revision operations are applied to the affected
shared-file family so one family-table member is not left with a contradictory lock or
object history.

Different drawing files may still be associated with those BOM objects. The exact
object iteration and file pointers are stored per BOM item while the shared native-file
workflow is coordinated as a family.

## Database Model

### `bom_revisions`

Stores each item revision, lifecycle state, creator, release identity, date, and note.

### `bom_iterations`

Stores automatically numbered object checkpoints, check-in note, source commit, creator,
date, and the checked-in BOM attribute/file-pointer snapshot.

### `bom_iteration_bindings`

Stores the immutable direct-child configuration for one assembly iteration:

- Parent iteration
- Usage relationship
- Child BOM object
- Exact child revision
- Exact child iteration
- Quantity
- Sort order

### `bom_working_bindings`

Stores editable child-version selections while an assembly is checked out. These rows
are discarded by Undo Checkout or converted into an immutable snapshot by commit
finalization.

### `bom.current_revision_id` and `bom.current_iteration_id`

Provide fast access to the version shown by the active project BOM without scanning
history.

### `bom.pending_revision_code`

Stores the target revision only while a Released item is checked out. The pointer to
the Released iteration does not move. Commit consumes this value to create the target
revision `.1`; Undo Checkout clears it.

## Migration Behavior

Migration 22 is backward compatible with the existing SQLite database.

- Existing BOM rows keep their visible revision code.
- Because older databases have no reconstructable object-iteration ledger, each existing
  row is initialized as iteration `.1` of its current revision.
- Existing assembly relationships are captured as the `.1` exact configuration.
- Existing file versions, commits, snapshots, baselines, locks, issues, and project
  versions are not renamed or removed.
- New baseline rows record `object_iteration_id`; older baseline rows remain readable
  with that value empty.
- All subsequent commit finalizations produce complete iteration history.

The migration cannot infer historical assembly configurations that were never stored.

Migration 23 adds the nullable `bom.pending_revision_code` field. Existing objects,
revisions, iterations, bindings, and locks are unchanged, and all existing rows start
with no pending revision.

## Relationship to Commits, Snapshots, and Baselines

- A **commit** is the controlled change transaction. Its successful finalization creates
  the next object iteration and supplies the source commit reference.
- A **snapshot** captures project state for comparison and diagnostics. Snapshot data
  includes checked-in object iteration IDs and exact child bindings alongside Creo file
  checksums.
- A **baseline** selects approved files/configuration for delivery. Each baseline file
  row records the selected BOM object iteration, so its manifest identifies an exact
  object version rather than a moving "latest" reference.
- A **project version** copies a complete configuration into another project-version row
  and remaps all internal IDs.

## Individual Occurrences

Current exact binding is stored at the direct usage relationship represented by
`bom_children`. Quantity and order are frozen with the usage. Nexus does not yet store a
separate identity and transformation for every individual Creo component occurrence.

Future occurrence support can extend this design with stable Creo occurrence IDs,
reference designators, suppression state, and placement transforms without changing the
revision/iteration model.

## Verification Checklist

1. Existing item opens as `<current revision>.1` after migration.
2. Check Out does not create an iteration.
3. Undo Checkout restores attributes and structure and does not create an iteration.
4. A child commit creates the next child iteration.
5. The parent remains bound to the older child until explicitly updated.
6. Update Child Versions modifies only the checked-out working assembly.
7. Parent commit creates the next parent iteration with the selected exact bindings.
8. Released checkout requires a target revision and leaves the Released iteration
   unchanged until commit.
9. Undoing a Released checkout clears its pending target and creates no revision.
10. New revision accepts the configured drawing-revision format and starts at `.1`.
11. Creating a project version remaps bindings to the copied BOM IDs.
12. Creo `.prt.N`, `.asm.N`, and `.drw.N` numbers remain independent of PLM iteration.
